## 2. Project Objective

ScamShield AI is a web application that helps users identify potentially fraudulent messages, phishing emails, suspicious SMS messages, and malicious URLs.

The application must:

1. Analyze email and SMS text using a trained machine-learning model.
2. Analyze URLs using URL features and a trained machine-learning model.
3. Produce a risk assessment with evidence-based explanations.
4. Support messages containing one or more URLs.
5. Maintain scan history and analytics.
6. Provide an intuitive, responsive user interface.
7. Include a complete model-training and evaluation pipeline.
8. Be deployable using documented production configuration.

This is an educational cybersecurity project. It must not claim perfect accuracy or guarantee that any URL or message is safe.

## 4. Architecture

Implement three independently runnable services.

### Frontend
Responsible for the user interface, input validation, scan submission, results, history, and analytics.

### Express backend
Responsible for authentication, authorization, request validation, rate limiting, scan orchestration, MongoDB persistence, and communication with the ML service.

### Python ML service
Responsible for loading trained models, extracting features, running predictions, and returning structured results.

The intended request flow is:

React frontend → Express backend → FastAPI ML service → Express backend → MongoDB persistence → React result display.

Express must be the public application API. Do not expose internal ML-service credentials or internal service URLs to the browser.

Use versioned and documented APIs. Keep the frontend, backend, and ML service decoupled enough that each can be tested independently.

## 7. Phase Two: Dataset Acquisition and Data Preparation

### URL dataset

Use the official UCI PhiUSIIL Phishing URL Dataset as the initial URL-classification dataset:

https://archive.ics.uci.edu/dataset/967/phiusiil-phishing-url-dataset

Inspect the dataset documentation before training.

Determine:
- Actual target-label column.
- Actual label mapping.
- Feature names and data types.
- Missing values.
- Duplicate records.
- Class distribution.
- Which features can genuinely be extracted from a submitted URL without visiting the destination website.

Do not assume label meanings or column names.

If a dataset feature requires webpage content, external metadata, or historical information unavailable to the live scanner, do not silently use it as though it were available at prediction time.

Use a consistent feature contract between training and inference.

### Text dataset

Choose a suitable, legally accessible, labelled dataset for phishing and scam text classification.

A public SMS spam dataset may be used for an initial spam-versus-ham baseline, but clearly distinguish spam detection from phishing detection. Do not misrepresent spam labels as phishing labels.

Document the dataset source, license or terms, label mapping, known limitations, and preprocessing steps.

If dataset downloading is unavailable, provide clear manual download instructions and graceful error handling.

### Data preparation

Implement reproducible scripts for:
- Loading data.
- Inspecting schema and labels.
- Handling missing values.
- Removing or analyzing duplicates.
- Splitting training, validation, and test data.
- Avoiding data leakage.
- Saving data statistics and training configuration.

Fit learned preprocessing only on the training data.

Use a held-out test set and avoid duplicate or near-duplicate leakage across splits. Where appropriate, group related URLs or domains before splitting to obtain a more realistic evaluation.

Do not fabricate datasets, training metrics, or successful download results.

Requirements:

1. Load and validate the selected dataset.
2. Validate target labels and input features.
3. Establish a reproducible train/validation/test split.
4. Build a baseline Logistic Regression model.

10. Generate an evaluation report and confusion matrix.
11. Record dependency versions and a model version identifier.

Implement a reusable URL feature extractor that accepts a URL string and returns exactly the feature schema expected by the saved model.

Start with robust lexical URL features such as:
- URL length.
- Hostname length.
- Number of subdomains.
- IP-address hostname indicator.
- Presence of user-information delimiters.
- Suspicious encoding or URL patterns.
- Path and query characteristics.

Create unit tests for normal URLs, malformed inputs, Unicode hostnames, IPv4 and IPv6 literals, unusual ports, percent-encoding, query strings, fragments, and deceptive hostname structures.

## 15. Phase Ten: Cybersecurity Requirements

The scanner must be designed defensively.

Critical rules:

1. Do not automatically visit submitted URLs in the MVP.
2. Parse and analyze URL strings without making outbound requests.
3. If external reputation checks are added later, protect against SSRF, DNS rebinding, redirects to internal hosts, private IP ranges, and unsafe protocols.
4. Never execute downloaded HTML, JavaScript, or files from submitted URLs.
5. Render untrusted message content as text, not trusted HTML.
6. Protect cookies using appropriate HttpOnly, Secure, and SameSite settings.
7. Validate all inputs on the server.
8. Restrict CORS and apply rate limits.
9. Do not leak environment variables, stack traces, secrets, or personal content in logs.
10. Keep dependencies updated and check for known vulnerabilities.
11. Enforce ownership checks on every user-specific operation.
12. Do not use real personal messages as training data without suitable permission and privacy safeguards.

Document limitations and security decisions.
